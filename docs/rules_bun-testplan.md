# rules_bun 테스트 계획

> 선행: [`rules_bun-plan.md`](rules_bun-plan.md) (실행 계획), [`rules_bun-design.md`](rules_bun-design.md) (아키텍처)
> 이 문서: **어떤 테스트를 먼저 쓸 것인가**. TDD의 입력이다.

---

## 0. 왜 이 문서가 필요한가

지금까지 만든 테스트는 전부 **사후에** 붙였고, 그중 둘은 가짜였다.

| 가짜 테스트 | 왜 통과했나 | 발견 |
|---|---|---|
| `hardening_test` (1차) | 공격 파일을 `bazel-out`에 만들었는데 Bun은 **cwd**의 `bunfig.toml`을 읽는다 | 사후 변이 테스트 |
| `build_test` 3종 | `--platforms`를 걸지 않아 **호스트에서 같은 걸 세 번** 빌드 | 사후 변이 테스트 |

둘 다 **초록불이었고, 변이를 넣어보기 전까지 아무도 몰랐다.** TDD는 이걸 구조적으로 막는다 — 먼저 쓴 테스트는 반드시 빨간불부터 봐야 하므로, 아무것도 검증하지 않는 테스트는 빨간불이 안 나와서 즉시 드러난다.

그래서 이 문서의 모든 케이스에 **변이 시나리오**를 함께 적는다. "이 테스트가 진짜인지 어떻게 확인하는가."

## 1. 테스트 층과 한계

층마다 잡을 수 있는 것이 다르다. **경계를 착각해서 이미 한 번 당했다.**

| 층 | 도구 | 잡는 것 | **못 잡는 것** |
|---|---|---|---|
| **단위** | `unittest` (skylib) | 순수 Starlark 로직 | Bazel과의 상호작용 전부 |
| **분석** | `analysistest` | 액션의 `argv`·`inputs`·`outputs`·`mnemonic`, provider 필드 | **액션의 실행 결과.** 플래그가 붙었다는 것과 그게 효과가 있다는 것은 다르다 |
| **실행** | test rule (`test = True`) | 실제 산출물 내용, 런타임 시맨틱 | 다른 플랫폼 |
| **플랫폼** | `with_platform` + `build_test` | 크로스 컴파일 해석 | 그 플랫폼에서의 **실행** (실행기 없음) |
| **증분** | 스크립트 (빌드 → 변경 → 재빌드) | 캐시 무효화·재실행 액션 수·산출물 동일성 | `bazel test` 로 표현 불가. **CI 나 수동 절차가 필요하다** |

> **증분 층은 `bazel test` 타겟이 될 수 없다.** 두 번 빌드해서 비교해야 하기
> 때문이다. L-X2·L-R3·K-X3 이 여기 속한다. CI 를 두지 않기로 하면 이 케이스들은
> **자동 회귀 방어가 없다** — 그 사실을 알고 결정해야 한다.

**실증** — 첫 스모크 룰이 `bun --version`을 썼는데 그건 `preload`를 타지 않는다. 분석 테스트였다면 "플래그가 붙었다"는 통과하고 "공격이 막힌다"는 검증하지 못했을 것이다. 그래서 하드닝은 **두 층**(`hardening_emitted_test` + `hardening_test`)으로 나뉘어 있다.

**규칙 — 계약에는 두 층이 필요하다.** 하나는 "규약대로 만들어졌는가"(분석), 다른 하나는 "그 규약이 효과가 있는가"(실행).

## 2. 케이스 도출 방법

`unit-test` 스킬의 방법을 룰에 적용한다.

- **EP(등가 분할)** — 입력을 동치류로 나눈다. 같은 류에서는 한 케이스만.
- **BVA(경계값)** — 0개 / 1개 / 다수 / 상한.
- **예외** — 실패해야 하는 입력. **조용히 실패하는 것이 가장 위험하다.**

여기에 룰 고유의 두 축을 더한다.

- **재현성** — 같은 입력이면 같은 출력인가. 주변 상태가 새는가.
- **플랫폼** — 5개 플랫폼에서 해석되는가.

## 3. 리팩터 단계 (`plan.md` §3) 의 검증

리팩터는 기존 테스트 10개가 회귀를 잡는다. 다만 **공개 API를 바꾸는 두 단계**에는 케이스를 추가한다.

| 단계 | 추가 케이스 | 층 | 변이 시나리오 |
|---|---|---|---|
| §3.1 룰셋 툴체인 | 룰셋 워크스페이스에서 툴체인 필요 테스트가 **돈다** | 실행 | 룰셋 `MODULE.bazel` 의 `dev_dependency` 블록 **전체 삭제** → 툴체인 해석 실패 |
| §3.1 | 소비자가 **다른 버전을 선택할 수 있다** | 실행 | `dev_dependency = True` 만 제거 → 소비자가 받는 Bun 버전이 룰셋 값으로 바뀌는가 |

> **변이가 유효하려면 소비자가 룰셋과 다른 버전을 선언해야 한다.** 둘 다
> 1.4.2 면 `dev_dependency` 를 떼도 결과가 같아 **죽은 변이**가 된다. §3.9 가
> e2e 를 1.3.0 으로 두는 이유다. 실측 확인: 소비자 1.3.0 기준으로
> `dev_dependency` 제거 → 1.4.2 로 끌려감, 원복 → 1.3.0.
| §3.2 provider 개명 | `BunRuntimeInfo` 필드 3개가 채워진다 | 분석 | 필드 하나 제거 → 실패 |
| §3.2 | `BunInfo` 라는 이름이 코드 어디에도 없다 | **수동** | `grep -rn "BunInfo" tools/rules_bun` — `bazel test` 로 강제되지 않는다. 완료 판정용 체크이지 회귀 방어가 아니다 |

## 4. `bun_library`

컴파일 단위. 설계 §2.7이 *"패키지를 자기 cwd·자기 tsconfig로 컴파일한다"* 로 확정했다.

### 4.1 해피

| # | 케이스 | 층 | 변이 |
|---|---|---|---|
| L-H1 | 단일 `.ts` → 산출물 생성 | 실행 | 산출물 선언 제거 → `no generating action` |
| L-H2 | 산출물이 **실제로 실행 가능**하다 | 실행 | 컴파일 결과를 빈 파일로 → 실행 실패 |
| L-H3 | `deps` 의 산출물이 전이된다 | 분석 | `transitive` 누락 → 의존 파일이 inputs에 없음 |
| L-H4 | `BunInfo` provider 필드가 채워진다 | 분석 | 필드 하나 비움 → 실패 |
| L-H5 | 하드닝 인자가 방출된다 | 분석 | `bun_action` 우회 → 실패 |

### 4.2 경계 (BVA)

| # | 케이스 | 층 | 변이 |
|---|---|---|---|
| L-B1 | `srcs` 파일 1개 | 실행 | 그 파일을 수정 → 재컴파일되는가 |
| L-B2 | `srcs` 파일 다수 (param file 전환 임계 초과) | 분석 | param file 미사용으로 되돌림 → argv 길이 폭증 확인 |
| L-B3 | `deps` 0개 | 분석 | `deps` 를 mandatory 로 → 실패 |
| L-B4 | 전이 깊이 3단 이상 — inputs 에 3단째 파일이 들어간다 | 분석 | `depset(transitive=...)` 를 `direct` 만으로 → 3단째 파일이 inputs 에서 빠지는가. **`to_list()` 로 바꾸는 변이는 죽어 있다**(결과가 같아 테스트가 초록불이다) |
| L-B5 | 비ASCII 경로·파일명 | 실행 | 경로를 인용 없이 셸에 넘기도록 → 깨지는가 |

### 4.3 예외 — **설계 문서가 이미 실측한 지뢰**

**이 절이 이 문서의 핵심이다.** §2.5·§2.7·§2.8은 실측으로 확인된 파손인데 지금은 글로만 있다. 테스트로 전환하면 실행 가능한 보장이 된다.

| # | 케이스 | 근거 | 층 | 변이 |
|---|---|---|---|---|
| **L-X1** | `tsconfig` 가 액션 **입력으로 선언**된다 | §2.5 — 선언 안 하면 캐시 키에 안 들어가 **증분 빌드가 틀린 답을 준다** | 분석 | `inputs` 에서 tsconfig 제거 → 실패 |
| **L-X2** | `tsconfig` 를 바꾸면 **재컴파일된다** | §2.5 | 실행 | tsconfig 를 입력에서 빼고 수정 → 캐시 히트로 옛 결과가 나오는가 |
| **L-X3** | `emitDecoratorMetadata` 가 **살아남는다** | §2.5 — cwd 의 tsconfig 가 결정한다. 어긋나면 **무음 파손** | 실행 | 액션 cwd 를 패키지 밖으로 → `design:paramtypes` 가 `undefined` 되는가 |
| **L-X4** | 패키지 이름으로 `extends` 하면 **실패하거나 경고한다** | §2.7 — `extends: "@cfg/base/tsconfig.json"` 은 Bun 에서 조용히 무시된다. tsc 는 통과하고 런타임만 다르다 | 실행 | 상대경로 `extends` 와 결과 비교 |
| **L-X5** | `extends` 체인의 **대상 파일도 입력**이다 | §2.7 | 분석 | 체인 파일을 입력에서 제거 → 그 파일 수정이 반영되는가 |
| **L-X6** | 순환 의존이 **런타임에 터지지 않는다** | §2.8 — `emitDecoratorMetadata` + 순환은 ESM TDZ 로 `ReferenceError`. 소스·esm·cjs 전부 동일 | 실행 | `import type` 규약을 어긴 픽스처로 산출물을 **실행** → `ReferenceError` 가 나는가. **분석 층으로는 불가능하다** — Starlark 는 `.ts` 를 파싱하지 않는다 |

> **L-X4·L-X6은 "실패하는 것이 정답"인 케이스다.** 조용히 통과하면 그게 버그다.

## 5. `bun_binary`

실행 파일. 설계 §4.4가 런처 요구사항을 정했다.

| # | 케이스 | 근거 | 층 |
|---|---|---|---|
| B-H1 | `bazel run` 으로 실행된다 | — | 실행 |
| B-H2 | runfiles 에서 의존 파일을 찾는다 | §7.2 | 실행 |
| B-H3 | 런처가 **패키지 디렉터리로 cd** 한다 | §2.7 — cwd 가 tsconfig 시맨틱을 결정한다 | 실행 |
| B-H4 | 런처가 `--no-install` 로 실행한다 | §2.1 E | **실행** — 런처는 액션이 아니라 **생성된 파일**이다. argv 가 아니라 파일 내용이라 분석 층에서 못 본다 |
| B-X1 | runfiles 심볼릭 링크가 **소스 트리로 탈출하지 않는다** | §2.2 C — realpath 로 풀린다 | 실행 |
| B-X2 | 같은 runfiles 경로에 두 파일이 매핑되지 않는다 | §7.2 | **실행** — 실측 결과 Bazel 9.2.0 은 **충돌을 빌드 실패로 만들지 않는다**(`Build completed successfully`, 해당 경로는 생성조차 안 됨). 즉 룰이 스스로 막아야 하고, 검증은 runfiles 트리를 직접 걸어야 한다 |
| B-P1 | Windows 런처(`.cmd`)가 생성된다 | `PLATFORMS` 가 windows-x64 를 선언한다 | 분석 |

> **B-P1 주의.** 현재 `hardening_test` 의 런처는 `#!/bin/sh` 인라인이고 Windows 에서 깨진다. `rules_ruby` 는 `.sh.tpl`/`.cmd.tpl` 로 분리한다. **실행기가 없어 실행 검증은 불가하므로 분석 층까지만 보장한다.**

> §0 이 열거한 두 가짜 테스트와 같은 구조 — 초록불이고 변이를 넣어도 초록불이다.

## 10. TDD 진행 방식

케이스 하나마다 이 순서를 지킨다.

```
1. 테스트를 쓴다
2. 빨간불을 확인한다            ← 건너뛰지 않는다
3. 최소 구현
4. 초록불
5. 변이를 넣어 다시 빨간불인지 확인   ← 이 표의 "변이" 칸
6. 변이 원복
```

**2번과 5번이 이 문서의 존재 이유다.** 지금까지 가짜 테스트 둘이 나온 건 2번을 안 했기 때문이고, 그걸 발견한 건 5번을 사후에 했기 때문이다.

### 전제 — 격리와 스텁 없이는 red-green 이 성립하지 않는다

미구현 심볼을 `load` 하면 **그 패키지 전체가 죽는다.** 실측:

```
bun/tests/BUILD.bazel 에 미구현 심볼 load 1줄 추가
→ ERROR: package contains errors: bun/tests
→ 기존 semver_test_0 도 "target not declared" 가 된다
```

즉 "그 케이스만 red" 가 아니라 **기존 테스트 전부가 실행 불가**가 되고,
red 의 의미도 왜곡된다 — assertion 실패가 아니라 Starlark load 에러라
무엇을 구현해야 통과하는지 테스트가 알려주지 못한다.

**대응 두 가지를 반드시 함께 쓴다.**

1. **패키지 격리** — 새 룰의 테스트는 `bun/tests/<rule>/BUILD.bazel` 로
   분리해 기존 테스트와 다른 패키지에 둔다.
2. **실패 스텁 선행** — `load()` 가 성공하도록 항상 실패하는 최소 룰을
   먼저 커밋한다.

   ```python
   def _bun_library_impl(ctx):
       fail("bun_library: 미구현")

   bun_library = rule(implementation = _bun_library_impl, attrs = {...})
   ```

   이러면 케이스가 **assertion 실패로 red** 가 되고, 최소 구현을 채워
   green 으로 만드는 정상 사이클이 성립한다.

### 순서

```
§3 리팩터 검증          (기존 테스트가 회귀를 잡음)
  ↓
L-X1 ~ L-X6             지뢰부터. 가장 비싼 결함이고 설계 문서가 이미 답을 안다
  ↓
L-H1 ~ L-H5             해피
  ↓
L-B, L-N, L-R, L-P      경계·네거티브·재현성·플랫폼
  ↓
B-*, T-*                bun_binary, bun_test
  ↓
U-*, E-*, K-*           번들·실행파일·링크 레이어
```

**지뢰(L-X)를 먼저 쓰는 이유** — 해피 케이스는 구현하면 자연히 통과한다. 지뢰는 구현이 끝난 뒤에 확인하면 이미 잘못된 구조 위에 쌓인 상태다. §2.7의 무음 파손은 특히 그렇다.
