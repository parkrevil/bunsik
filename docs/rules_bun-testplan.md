# rules_bun 테스트 계획

> 선행: [`rules_bun-plan.md`](rules_bun-plan.md) (실행 계획), [`rules_bun-design.md`](rules_bun-design.md) (아키텍처)
> 이 문서: **어떤 테스트를 먼저 쓸 것인가**. TDD의 입력이다.

---

## 0. 왜 이 문서가 필요한가

지금까지 만든 테스트는 전부 **사후에** 붙였고, 그중 둘은 가짜였다.

| 가짜 테스트 | 왜 통과했나 | 발견 |
|---|---|---|
| `hardening_test` (1차) | 공격 파일을 `bazel-out`에 만들었는데 Bun은 **cwd**의 `bunfig.toml`을 읽는다 | 사후 변이 테스트 |
| `build_test` 3종 | `--platforms`를 걸지 않아 **호스트에서 같은 걸 세 번** 빌드 | 사후 변이 테스트 |

둘 다 **초록불이었고, 변이를 넣어보기 전까지 아무도 몰랐다.** TDD는 이걸 구조적으로 막는다 — 먼저 쓴 테스트는 반드시 빨간불부터 봐야 하므로, 아무것도 검증하지 않는 테스트는 빨간불이 안 나와서 즉시 드러난다.

그래서 이 문서의 모든 케이스에 **변이 시나리오**를 함께 적는다. "이 테스트가 진짜인지 어떻게 확인하는가."

---

## 1. 테스트 층과 한계

층마다 잡을 수 있는 것이 다르다. **경계를 착각해서 이미 한 번 당했다.**

| 층 | 도구 | 잡는 것 | **못 잡는 것** |
|---|---|---|---|
| **단위** | `unittest` (skylib) | 순수 Starlark 로직 | Bazel과의 상호작용 전부 |
| **분석** | `analysistest` | 액션의 `argv`·`inputs`·`outputs`·`mnemonic`, provider 필드 | **액션의 실행 결과.** 플래그가 붙었다는 것과 그게 효과가 있다는 것은 다르다 |
| **실행** | test rule (`test = True`) | 실제 산출물 내용, 런타임 시맨틱 | 다른 플랫폼 |
| **플랫폼** | `with_platform` + `build_test` | 크로스 컴파일 해석 | 그 플랫폼에서의 **실행** (실행기 없음) |

**실증** — 첫 스모크 룰이 `bun --version`을 썼는데 그건 `preload`를 타지 않는다. 분석 테스트였다면 "플래그가 붙었다"는 통과하고 "공격이 막힌다"는 검증하지 못했을 것이다. 그래서 하드닝은 **두 층**(`hardening_emitted_test` + `hardening_test`)으로 나뉘어 있다.

**규칙 — 계약에는 두 층이 필요하다.** 하나는 "규약대로 만들어졌는가"(분석), 다른 하나는 "그 규약이 효과가 있는가"(실행).

## 2. 케이스 도출 방법

`unit-test` 스킬의 방법을 룰에 적용한다.

- **EP(등가 분할)** — 입력을 동치류로 나눈다. 같은 류에서는 한 케이스만.
- **BVA(경계값)** — 0개 / 1개 / 다수 / 상한.
- **예외** — 실패해야 하는 입력. **조용히 실패하는 것이 가장 위험하다.**

여기에 룰 고유의 두 축을 더한다.

- **재현성** — 같은 입력이면 같은 출력인가. 주변 상태가 새는가.
- **플랫폼** — 5개 플랫폼에서 해석되는가.

## 3. 리팩터 단계 (`plan.md` §3) 의 검증

리팩터는 기존 테스트 10개가 회귀를 잡는다. 다만 **공개 API를 바꾸는 두 단계**에는 케이스를 추가한다.

| 단계 | 추가 케이스 | 층 | 변이 시나리오 |

## 4. `bun_library`

컴파일 단위. 설계 §2.7이 *"패키지를 자기 cwd·자기 tsconfig로 컴파일한다"* 로 확정했다.

### 4.1 해피

| # | 케이스 | 층 | 변이 |
|---|---|---|---|
| L-H1 | 단일 `.ts` → 산출물 생성 | 실행 | 산출물 선언 제거 → `no generating action` |
| L-H2 | 산출물이 **실제로 실행 가능**하다 | 실행 | 컴파일 결과를 빈 파일로 → 실행 실패 |
| L-H3 | `deps` 의 산출물이 전이된다 | 분석 | `transitive` 누락 → 의존 파일이 inputs에 없음 |

### 4.3 예외 — **설계 문서가 이미 실측한 지뢰**

**이 절이 이 문서의 핵심이다.** §2.5·§2.7·§2.8은 실측으로 확인된 파손인데 지금은 글로만 있다. 테스트로 전환하면 실행 가능한 보장이 된다.

| # | 케이스 | 근거 | 층 | 변이 |
|---|---|---|---|---|
| **L-X1** | `tsconfig` 가 액션 **입력으로 선언**된다 | §2.5 — 선언 안 하면 캐시 키에 안 들어가 **증분 빌드가 틀린 답을 준다** | 분석 | `inputs` 에서 tsconfig 제거 → 실패 |
| **L-X2** | `tsconfig` 를 바꾸면 **재컴파일된다** | §2.5 | 실행 | tsconfig 를 입력에서 빼고 수정 → 캐시 히트로 옛 결과가 나오는가 |
| **L-X3** | `emitDecoratorMetadata` 가 **살아남는다** | §2.5 — cwd 의 tsconfig 가 결정한다. 어긋나면 **무음 파손** | 실행 | 액션 cwd 를 패키지 밖으로 → `design:paramtypes` 가 `undefined` 되는가 |
| **L-X4** | 패키지 이름으로 `extends` 하면 **실패하거나 경고한다** | §2.7 — `extends: "@cfg/base/tsconfig.json"` 은 Bun 에서 조용히 무시된다. tsc 는 통과하고 런타임만 다르다 | 실행 | 상대경로 `extends` 와 결과 비교 |
| **L-X5** | `extends` 체인의 **대상 파일도 입력**이다 | §2.7 | 분석 | 체인 파일을 입력에서 제거 → 그 파일 수정이 반영되는가 |
| **L-X6** | 순환 의존이 **분석 단계에서 잡힌다** | §2.8 — `emitDecoratorMetadata` + 순환은 ESM TDZ 로 `ReferenceError`. 소스·esm·cjs 전부 동일 | 실행 | 순환 픽스처로 빌드 → 런타임에야 터지는가, 빌드에서 잡히는가 |

> **L-X4·L-X6은 "실패하는 것이 정답"인 케이스다.** 조용히 통과하면 그게 버그다.

## 9. 픽스처 배치

`rules_js` 가 `js/private/test/data/` 에 실물 파일을 둔다. 같은 방식으로 간다.

```
bun/tests/fixtures/
  simple/            단일 .ts + tsconfig.json          L-H1, L-H2
  deps/              라이브러리 2개 + 의존 관계          L-H3, L-B4
  decorators/        emitDecoratorMetadata 사용         L-X3
  extends-relative/  상대경로 extends                   L-X4 (통과해야 함)
  extends-package/   패키지 이름 extends                L-X4 (실패해야 함)
  circular/          forwardRef 순환                    L-X6
  many-sources/      파일 다수                          L-B2
```

각 픽스처는 **최소**로 유지한다. 픽스처가 커지면 무엇을 검증하는지 흐려진다.

## 10. TDD 진행 방식

케이스 하나마다 이 순서를 지킨다.

```
1. 테스트를 쓴다
2. 빨간불을 확인한다            ← 건너뛰지 않는다
3. 최소 구현
4. 초록불
5. 변이를 넣어 다시 빨간불인지 확인   ← 이 표의 "변이" 칸
6. 변이 원복
```

**2번과 5번이 이 문서의 존재 이유다.** 지금까지 가짜 테스트 둘이 나온 건 2번을 안 했기 때문이고, 그걸 발견한 건 5번을 사후에 했기 때문이다.

### 순서

```
§3 리팩터 검증          (기존 테스트가 회귀를 잡음)
  ↓
L-X1 ~ L-X6             지뢰부터. 가장 비싼 결함이고 설계 문서가 이미 답을 안다
  ↓
L-H1 ~ L-H5             해피
  ↓
L-B, L-N, L-R, L-P      경계·네거티브·재현성·플랫폼
  ↓
B-*, T-*                bun_binary, bun_test
  ↓
U-*, E-*, K-*           번들·실행파일·링크 레이어
```

**지뢰(L-X)를 먼저 쓰는 이유** — 해피 케이스는 구현하면 자연히 통과한다. 지뢰는 구현이 끝난 뒤에 확인하면 이미 잘못된 구조 위에 쌓인 상태다. §2.7의 무음 파손은 특히 그렇다.
